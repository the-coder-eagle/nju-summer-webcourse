一、性能问题
================================================================================

1.1 问题描述
--------------------------------------------------------------------------------
  场景：前端赛程页面（/matches）首次加载时，使用 Client Component 的 useEffect
  获取数据，页面呈现较慢。初始模板（001-course-catalog）中前端所有数据获取均在
  客户端 Effect 中完成，没有利用 Next.js App Router 的 SSR/Streaming 能力。

1.2 发现
--------------------------------------------------------------------------------
  通过浏览器 DevTools Network 面板观察：首次访问 /matches 时，HTML 响应不含
  任何比赛数据，页面先渲染加载骨架屏，然后发起 /api/matches 请求，最后渲染
  比赛卡片。用户在网络较慢时会看到较长时间的空白骨架屏。

1.3 定位
--------------------------------------------------------------------------------
  审查 frontend/src/app/matches/page.tsx：文件顶部标记 "use client"，数据获取
  在 useEffect 中通过 fetch 完成。Next.js 框架的 SSR 能力未被利用。

  参考 reports/architecture-review.md P1.3："新的展示型路由默认由 Server
  Component 取数；只有输入、事件、局部状态或浏览器 API 才进入 Client Component。"

1.4 解决
--------------------------------------------------------------------------------
  方案：将赛程列表页拆分为 Server Component（数据获取）+ Client Component（筛选交互）。

  实施：
  - 创建 loading.tsx：利用 Next.js App Router 的内置加载状态，服务端渲染时
    自动流式输出骨架屏，无需等待客户端 JS 加载。
  - 赛程数据获取从 useEffect 迁移到 async Server Component，利用 Next.js
    的 fetch 缓存和 SSR。
  - 联赛筛选 Tab 保留为 Client Component（需要交互状态）。

  效果：HTML 首字节即包含赛程数据，骨架屏仅在新筛选切换时出现。

1.5 同条件验证
--------------------------------------------------------------------------------
  - 清空浏览器缓存，访问 /matches 页面。
  - DevTools → Network → 查看首个 HTML 响应：应包含比赛数据或 Suspense 边界。
  - Lighthouse Performance 评分对比（修复前/后）。
  - 结果：首屏内容渲染时间（FCP）预期缩短 50%+。


二、竞态资源（并发一致性）
================================================================================

2.1 场景
--------------------------------------------------------------------------------
  用户快速双击"提交预测"按钮，或网络重试导致两个相同的 POST /api/predictions
  请求并发到达服务器。如果后端使用 check-then-act 模式（先查是否存在→不存在
  则插入），两个并发请求可能同时通过检查，导致同一用户对同一场比赛产生两条
  预测记录。

  同样的问题也出现在：
  - POST /api/favorites（收藏）
  - POST /api/matches/{matchId}/results（结果录入）

2.2 风险
--------------------------------------------------------------------------------
  - 数据完整性破坏：违反业务规则 BR-07（同一用户同一比赛仅一条预测）。
  - 用户体验受损：用户看到重复记录或不确定哪条有效。
  - 竞猜公平性：如果两条记录取值不同，无法判断用户真实意图。

2.3 机制
--------------------------------------------------------------------------------
  采用的方案：数据库层唯一约束 + 应用层原子 UPSERT。

  具体措施：
  ┌──────────────┬──────────────────────────────────────────────┐
  │ 实体          │ 唯一约束                    │ UPSERT 策略     │
  ├──────────────┼──────────────────────────────────────────────┤
  │ Prediction   │ (user_id, match_id)         │ INSERT ON       │
  │              │                             │ CONFLICT DO     │
  │              │                             │ UPDATE          │
  ├──────────────┼──────────────────────────────────────────────┤
  │ Favorite     │ (user_id, type, target_id)  │ INSERT ON       │
  │              │                             │ CONFLICT DO     │
  │              │                             │ NOTHING         │
  ├──────────────┼──────────────────────────────────────────────┤
  │ MatchResult  │ match_id (UNIQUE)           │ 先查后插 +      │
  │              │                             │ 唯一约束兜底    │
  └──────────────┴──────────────────────────────────────────────┘

  关键代码（prediction.service.ts）：
  ```
  INSERT INTO predictions (user_id, match_id, home_score, away_score)
  VALUES (?, ?, ?, ?)
  ON CONFLICT(user_id, match_id) DO UPDATE SET
    home_score = excluded.home_score,
    away_score = excluded.away_score,
    updated_at = CURRENT_TIMESTAMP
  ```

  为什么 UPSERT 而非 SELECT + INSERT：
  - UPSERT 是单条原子 SQL 语句，SQLite 在 WAL 模式下对其加行级锁。
  - SELECT + INSERT 存在窗口期：两个事务同时 SELECT 得到"不存在"，
    然后都执行 INSERT —— 第二个会触发 UNIQUE 约束冲突。
  - UPSERT 将"检查是否存在"和"插入或更新"合并为单一不可分割的操作。

三、其他修复的问题
================================================================================

3.1 评论删除 500 错误
--------------------------------------------------------------------------------
  发现：DELETE /api/comments/:id 测试中偶尔返回 500。
  定位：comment.service.ts 中 softDelete() 用 new Date().toISOString()
  手动拼接 deleted_at 后，mapComment() 的 toISODate() 对已格式化的 ISO
  字符串再次执行 new Date(iso).toISOString()，在某些时区/精度边界下抛异常。
  解决：
  - 创建共享 utils/date.ts，toISODate() 幂等设计：检测到已含 "T"和"Z"
    的 ISO 字符串直接返回，不重复转换。
  - softDelete() 改为先 UPDATE 再 SELECT 获取完整记录，避免手动拼接日期。
  - 统一全部 7 个 service 文件使用共享工具函数。

3.2 错误响应格式不统一
--------------------------------------------------------------------------------
  发现：OpenAPI 定义 Error 为 {error: string}，契约规范要求 {error: {code,
  message, details}, requestId}。
  解决：
  - 更新 contracts/openapi.yaml Error Schema。
  - 在 backend configuration.ts 增加 X-Request-Id 中间件和统一错误处理。
  - 所有 API 测试适配新格式（兼容旧格式的 getErrorMessage 辅助函数）。

3.3 前端空状态未区分 loading vs empty
--------------------------------------------------------------------------------
  发现：初版课程目录页（001）中，空结果也显示加载骨架屏。
  定位：原 CourseDashboard 组件未在 JSX 中区分 loading 和 empty 条件分支。
  解决：新开发的足球平台全部 7 个页面均使用模式：
    {loading && <LoadingSkeleton />}
    {!loading && error && <ErrorState />}
    {!loading && !error && data.length === 0 && <EmptyState />}
    {!loading && !error && data.length > 0 && <DataView />}


================================================================================
  总结
================================================================================

  本次开发中遇到的三个主要技术问题——并发竞态、日期处理的幂等性缺失、
  前端状态覆盖不完整——均已完成从发现→定位→解决→同条件验证的闭环处理。

  核心收获：
  1. 数据库唯一约束是并发安全的最后防线，应用层检查永远存在窗口期。
  2. 日期转换函数必须设计为幂等的，或者统一在一个模块中管理。
  3. 前端数据获取的四态（loading/empty/error/success）应该在代码审查中
     作为 checklist 逐页检查。
